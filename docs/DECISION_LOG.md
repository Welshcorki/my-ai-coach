## 2025-12-22

### 1. 맥락 인식(Context Awareness) 구현 방식: RAG Lite
- **상황 (Context):** 사용자가 PDF 교재를 업로드하여 로드맵을 생성하지만, 이후 채팅에서 AI가 교재 내용을 전혀 모른 채 일반적인 지식으로만 답변하는 문제가 발생함.
- **고려 대안:**
  1. **Full RAG (Vector DB):** 텍스트를 청크 단위로 임베딩하여 벡터 DB(Pinecone 등)에 저장하고 검색. 정확도는 높으나 구축 비용과 복잡도가 높음.
  2. **RAG Lite (Context Summary):** 로드맵 생성 시 전체 요약본을 만들어 RDB에 저장하고, 채팅 시 프롬프트에 통째로 주입.
- **결정 (Decision):** **RAG Lite 방식 채택.**
- **이유 (Reasoning):** 
  - 현재 사용하는 `gemini-2.5-flash` 모델은 컨텍스트 윈도우가 매우 커서(1M 토큰), 책 한 권 분량의 요약이나 목차 정보를 프롬프트에 직접 넣어도 무리가 없음.
  - 별도의 벡터 DB 인프라를 구축할 필요 없이 기존 RDB(SQLite/PostgreSQL) 스키마에 컬럼 하나만 추가하면 되어 구현 속도가 빠름.
- **구현 상세:**
  - `Roadmap` 테이블에 `context_summary` 컬럼 추가.
  - `plan.py`: 로드맵 생성 시 목차와 핵심 개념을 포함한 "상세 요약(약 2000자)"을 생성하도록 프롬프트 조정.
  - `chat.py`: 시스템 프롬프트에 해당 요약을 주입하고, "교재에 따르면..."과 같이 인용하여 답변하도록 페르소나 설정.

### 2. 퀴즈 시스템 구현 방식: 인터랙티브 UI 카드 (Tag Parsing)
- **상황:** 기존의 자연어 기반 퀴즈는 정오답 판별이 모호하고 사용자가 텍스트를 길게 입력해야 하는 UX 불편함이 있음.
- **고려 대안:**
  1. **텍스트 기반 퀴즈:** AI가 말로 질문하고 사용자가 글로 답변. 구현은 쉽지만 자동화가 어려움.
  2. **커스텀 UI 카드:** AI가 특정 데이터 포맷을 보내면 프론트엔드에서 객관식 버튼 UI로 렌더링.
- **결정 (Decision):** **커스텀 UI 카드 방식 채택 (태그 기반 파싱).**
- **이유 (Reasoning):** 
  - 사용자가 버튼 클릭만으로 답을 제출할 수 있어 모바일 등 다양한 환경에서 편리함(Gamification 요소).
  - 응답 내에 `[QUIZ]`와 같은 커스텀 태그를 사용하여 데이터와 일반 텍스트를 분리함으로써, 기존 채팅 로직을 크게 해치지 않고 기능을 확장할 수 있음.
  - 정답 시 자동으로 다음 턴을 유도하는 'handleAutoSend' 로직과의 연계가 용이함.
- **구현 상세:**
  - `chat.py`: 퀴즈 모드 시 `[QUIZ] {json} [/QUIZ]` 포맷을 준수하도록 프롬프트 고도화.
  - `useGemini.ts`: 정규표현식을 이용해 응답에서 퀴즈 데이터를 파싱하고 `ChatMessage` 객체에 바인딩.
  - `Chat.tsx`: `QuizCard` 컴포넌트를 구현하여 시각적 피드백(정답/오답 애니메이션) 및 자동 대화 전송 기능 연동.

## 2025-12-10

### 1. 배포 전략: Cloud Run + Docker Multi-stage Build
- **상황:** 프론트엔드(React)와 백엔드(FastAPI)가 분리된 프로젝트를 효율적으로 배포해야 함.
- **결정:** **단일 컨테이너 배포 (FastAPI serving Static Files).**
- **이유:** 
  - 소규모 프로젝트에서 프론트엔드와 백엔드 서버를 각각 띄우는 것은 관리 비용 낭비.
  - Docker Multi-stage build를 이용해 프론트엔드를 빌드하고, 결과물(`static/`)을 백엔드 이미지가 서빙하도록 통합.
  - Google Cloud Run은 트래픽이 없을 때 인스턴스를 0으로 줄여 비용 효율적임(Free Tier 활용).

### 2. 데이터베이스: SQLite (개발) -> Supabase (운영 예정)
- **상황:** Cloud Run은 로컬 파일시스템이 휘발성이라 SQLite 사용 시 재배포마다 데이터가 날아감.
- **결정:** 개발 단계에선 빠른 속도를 위해 SQLite 유지, 운영 단계에선 **Supabase (PostgreSQL)** 도입 결정.
- **이유:** Supabase는 완전 관리형이며, 추후 `pgvector`를 이용한 Full RAG 확장이 용이함.
